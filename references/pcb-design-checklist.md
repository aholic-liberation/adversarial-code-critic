# PCB 设计成果核查清单

适用对象：PCB 设计方案 / 原理图 / 布局布线 / 制造文件 / 设计流程文档。
依据来源：IPC-2221、IPC-2152、IPC-2141、JLCPCB 工艺能力预设（EDA 内置）、开源布局器（pyplacer / CadMust-Neo）与 Freerouting 的量化口径、Quilter 基准对比数据。

**本清单只列容易漏的点，不是豁免边界。有证据的问题即便不在此列照样要批。**

---

## 一、最常见的"假通过"陷阱（优先扫这些）

1. **铺铜网络被算作未布线**
   表现：连通性报告说 GND 未布线，但 GND 是靠铺铜连的。
   判定：先读 `eda.pcb_PrimitivePour.getAll()` 的 net 名单；名单内的网络视为已连通。
   反向风险：检查者据此把真缺陷也一并放过——要逐条看**不在**铺铜名单里的未布线网络。

2. **搬家后没重灌铺铜 → 误判为"元件间距问题"**
   表现：DRC 报 `Copper Region(Filled) to TH Pad/Via` 的 clearance error。
   真因：铺铜是在元件移动**之前**灌的，铜还停在哪。**不是布局违规**。
   判定：看报错对象里有没有 `Copper Region(Filled)`；有 → 先重灌再复查。
   修复：`pour.rebuildCopperRegion()`。**禁止用 delete+create 替代**——create 不生成填充。

3. **Netlist Error 混进设计缺陷里**
   表现：DRC 出现 `Netlist Error`（原理图与 PCB 网表不一致）。
   判定：这类是**流程/同步问题**，不是布线缺陷，要单独列出单独处理。

4. **声明的检查项无法执行，却报"通过"**
   最高危的一类。例：文档要求"线宽按载流校核"，但没有逐网络电流输入 → 该项实际未执行，而报告全绿。
   判定：把每一项检查追到它的**输入是否齐备**；输入缺失必须报"未执行"，不得报"通过"。

5. **未验证的 API / 步骤写成既定流程**
   表现：流程文档里列了工具，但从未调用过。
   判定：逐个追"是否实测过"。未实测的必须标 ⚠️ 并给出降级方案，不得当作既定步骤。

6. **把"运行时能枚举到"当成"公开 API"**
   表现：用 `Object.getOwnPropertyNames` 在运行时枚举到某个方法，就写进流程。
   反例（实测）：`pcb_Document.startAutoRouting` / `getAutoJobStatus` 运行时存在，但**不在官方类型定义里**，是内部方法；`getAutoJobStatus()` 直接抛错。而**公开**的等价入口是 `pcb_Document.autoRouting(props)`，返回 `{success, totalNetsCount, successNetsCount, failedNets[], duration}`。
   判定：**先查官方类型定义包 `@jlceda/pro-api-types`**（`npm install @jlceda/pro-api-types`，单文件 `index.d.ts`，注释带 `@beta`/`@public` 与示例），类型定义里没有的一律视为不稳定的内部实现。

7. **多步 API 只写了一步**
   反例（实测于类型定义）：制造文件导出是**两步**——`getGerberFile(...)` 返回 `File` 对象（**不是路径**），必须再接 `sys_FileSystem.saveFileToFileSystem(uri, file, fileName, force)` 才能落盘。
   且 `saveFileToFileSystem` 有路径白名单（见第 8 条）。
   判定：凡是"导出/保存/生成文件"类 API，必须确认返回值是文件对象还是路径，以及落盘由谁负责。

8. **参数错 → 误判为"API 不可用"（本清单域内连犯两次）**
   表现：调用失败（返回空/报错），就写"该 API 不可用"，其实是用错了参数。
   实例：
   - `lib_Device.getByLcscIds(['C6186'])` 返回 `[]` → 真相：该 C 编号在库内无匹配（换官方示例料号 `C1523` 仍为空，说明是库未同步，而非参数格式）
   - `saveFileToFileSystem` 报 `{"error":"路径不允许"}` → 真相：**路径白名单**，常见失败路径包括 `/tmp/`、用户文档目录（波浪号不展开）、父目录、纯文件名；落到 `<用户文档目录>/LCEDA-Pro/projects/` 可成功写盘
   判定：报告"不可用"之前，必须**穷举该 API 的关键参数维度**（路径要试：允许根目录 / 子目录 / 相对路径 / 波浪号 / 父目录；库查询要试：官方示例值 / 指定 libraryUuid / 单值 vs 数组）。
   只有"参数取证已穷举"才允许写 ❌。

9. **在只读工程上作业，改动不落盘，却以为完成了**
   表现：在示例工程（`example-projects/` 下的工程）上改了一堆东西，DRC 也过了、导出也出了，但**一个字节都没存进文件**。
   实测证据：`pcb_Document.save()` / `modifyProjectFriendlyName()` / `moveProject()` / `moveProjectToFolder()`（含 `folderUuid=undefined`）在该目录下的工程上**全部返回 `false`**。
   更隐蔽的一点：用 GUI「备份」功能生成的副本**仍落在同一个只读目录**，所以副本照样存不了盘——用户以为做完了备份，其实没有可写的工作副本。
   判定：动手前先验证工程可写（`save()` 是否返回 `true`），或确认工程位于 `~/文档/LCEDA-Pro/projects/`。**只读工程上的任何"完成"都是假象。**

10. **把环境模式的限制当成 API 本身的缺陷**
    表现：某个官方 API 实测返回 `false`/`undefined`，就写"该 API 不可用/不通"，当成设计缺陷写进结论。
    实例（本清单域内真实发生）：`copyProject` / `deleteProject` / `moveProject` / `getAllProjectsUuid` / `lib_Device.getByLcscIds` 全部失败，我全标成 ❌ 并断言"API 不通"。后来查环境才发现客户端处于**半离线模式**——而官方注释里早写着 `getLibrariesPaths` 需要「**全离线客户端环境**」。
    判定：报告"某 API 不可用"之前，**必须先记录运行模式**（`sys_Environment.isOnlineMode / isHalfOfflineMode / isOfflineMode`）。带模式前提的结论写成"在**当前模式**下不可用"；换模式后必须重跑预检重新判定。
    ❌ 只能表示"我这次没成功"，不能表示"这个能力不存在"。

11. **拿示例工程下结论**
    表现：在示例工程（`example-projects/` 下的 `.eprj2`）上测出失败，就断言 API 不可用。
    实例：`copyProject` 在示例工程上返回 `undefined`，我据此下了结论；被用户追问后到**普通工程**（`createProject` 新建的 `.eprj3`）复测三种参数组合，**同样失败** —— 结论恰好成立，但过程不严谨。
    判定：涉及"写 / 复制 / 删除工程"的 API，**必须在普通用户工程上复测**才允许下结论。可用 `dmt_Project.createProject` 造一个无害沙箱（它工作正常），测完清理。

12. **返回 `true` / `success` 就当生效**
    表现：API 返回成功就认为做完了，不再读状态。
    实例（本域内实测三次）：
    - `pcb_Document.importChanges()` 返回 `true` —— 其实在弹 GUI 确认框等点；后续调用顶掉弹窗 → **零传递**
    - `dmt_Schematic.modifySchematicPageTitleBlock()` 返回 `true` —— 图纸尺寸根本没变
    - `dmt_Project.copyProject()` 返回 `undefined` —— 磁盘无产物
    官方 issue #14 标题就是"文档声明的多个 eda.* API 未开放/返回 true 不生效/窗口挂起超 30s"。
    判定：**凡写操作，返回后必须再读一次状态验证**（例：改完读 `getAll().length`、改完读目标字段）。

13. **拿 DRC 条目的 `suffix` 当图元 ID 去定位/删除**
    表现：按 `obj1.suffix`（如 `e40686`）去 `pcb_PrimitiveLine.get(id)` 定位问题图元。
    实例：调用不报错，但返回对象**字段全 null**，于是误判"图元不存在 / 已丢失"。
    官方 issue #23.4 实证：**真正的图元 ID 在同一条目的 `objs` 数组里**，`suffix` 只是显示编号。
    判定：定位图元一律从 `objs` 取 ID；定位不到就报"无法定位"，不要报"图元不存在"。

14. **重复跑 DRC，把累积的 UI markers 当成新增违规**
    表现：一个验证周期内多次调 `pcb_Drc.check`，违规数越跑越多，以为设计在恶化。
    官方 issue #6.4 实证：**DRC 不幂等**，重复运行会累积 markers、虚增违规数。
    判定：**一个验证周期只跑一次 DRC**；想看变化就重新扁平化统计，别反复调 `check`。

15. **`Connection Error` 只归因一个原因**
    表现：GND 报连接错误，找到一个成因就收工。
    已知**至少两个独立成因**（各自实测）：
    - **零长度退化走线**（起点=终点，路由器留下）—— 删掉即清（本域实测）
    - **走线/过孔创建顺序**：先走线后过孔，坐标一致也不连，实测 660 条；改"先过孔后走线"后降到 16 条（官方 issue #23.1）
    判定：**两个都要查**。清完一个必须重跑 DRC 确认归零，不许"找到一个像样的原因就认为解释了全部"。

16. **靠坐标匹配判定引脚悬空**
    表现：`SCH_PrimitiveComponent.getAll()` 拿网络端口坐标和引脚坐标一比，不一致就判"悬空"。
    官方 issue #9 实证：该接口返回的是符号**锚点/主体中心**，不是箭头尖端电气接触点，差 **15~20 单位甚至更大**；
    坐标完全不同仍可能连通。
    判定：**永远不要仅因锚点坐标不匹配判悬空**。解不出电气端点时报 **"未验证"**。
    读引脚一律用 `getAllPinsByPrimitiveId()`，**不要从符号外观推断引脚顺序**。

17. **只看官方文档/类型定义，不翻仓库 Issue**
    表现：文档没写就以为没这回事；或文档写了就当一定对。
    实例（2026-10-16 检索官方 `easyeda-api-skill`，22 个 issue）：
    - 官方文档/类型定义说 `sch_PrimitiveWire.create` 收嵌套数组，issue #6 实测要扁平数组（**但部分版本嵌套可用**——版本差异，两种都要记）
    - 类型定义说 `pcb_PrimitiveLine.create` 支持板框层，运行时**只认铜层**（要改用 `PrimitivePolyline`）
    - 枚举全局"不总是注入" bridge 上下文（issue #6）
    - `getDsnFile()` 导出的层名/过孔重复/铺铜缺失/坐标取整偏差（issue #23.3）——**会让外部布线器把已连通网络判为未布通**
    判定：**结论要给证据等级，冲突要两条都记并说明适用条件**；别把单一来源当真理。

## 二、可量化判据

### 已标定（标准/公式确定，可直接判）

| 项 | 判据 | 来源 |
|---|---|---|
| 走线载流 | `I = k·ΔT^0.44·A^0.725`，A=线宽(mil)×铜厚(mil)，1oz=1.378mil；k=0.048 外层 / 0.024 内层 | IPC-2221 |
| 过孔纵横比校正 | 5:1→0.90 / 8:1→0.75 / 10:1→0.65 | IPC-TM-650 |
| 载流裕量 | 最窄段 ≥ 预期电流 × 1.5（**裕量倍数是经验值**） | 经验 |
| 连通性 | 未布线网络 = 0（Freerouting 的成功口径） | 社区共识 |
| DRC | error = 0 | EDA 规则 |
| 差分对间距/等长容差 | 从 EDA 规则集读，不要凭空给数 | EDA |

### 未标定（指标可信，阈值是猜的——必须标明）

| 项 | 理想 | 差 | 备注 |
|---|---|---|---|
| 绕线系数 = 走线总长 / HPWL | ≤1.4 | ≥3.0 | 阈值未经样本集标定 |
| 平均网络跨度 / 板对角线 | ≤0.15 | ≥0.60 | 同上 |
| 平均过孔数 / 网络 | ≤1.0 | ≥4.0 | 同上 |

**纪律**：结论贴近阈值边界时（如绕线系数 1.35），必须把原始数字交出并声明置信度低，**不得给"通过"**。

## 三、能力边界（AI 有权断言的范围）

**可以断言**：几何/连通性/DRC/载流的**计算结论**，制作文件是否成功导出。

**必须标「待验证」**：任何仿真类结论（SI / PI / EMC / 热）——没有仿真能力，不许给"应该能过 EMC"。

**必须由人核对**：封装与实物一致性；机械约束；市电及以上电压的安规间距。

**不许做**：把"我认为好看/合理"当作判据；把未标定的阈值当标准给出结论。

## 四、证据获取方式（怎么拿数字，而不是感觉）

```bash
# 连接前置
curl -s -m 5 http://127.0.0.1:49620/health        # 必须 edaConnected:true

# 量化评分（HPWL / 绕线系数 / 过孔数 / 连通性 / DRC / IPC-2221 载流）
eda-score
eda-score --json                                   # 机器可读

# 铺铜网络名单（判定连通性的前提）
# POST /execute: return (await eda.pcb_PrimitivePour.getAll()).map(p => p.getState_Net())
```

判定 API 是否存在**某个能力**时的正确方法（曾漏判过 `rebuildCopperRegion`，也误判过 `startAutoRouting`）：

1. **先查官方类型定义包** `@jlceda/pro-api-types`：`npm install @jlceda/pro-api-types`（1.8MB 单文件 `index.d.ts`），`grep -n "public <方法名>(" index.d.ts`。注释里带 `@beta` / `@public` 和示例代码。
   - 类型定义里有 → 公开 API，可放心写进流程
   - 只有运行时枚举到、类型定义里没有 → **内部方法，不稳定，不写进流程**
2. **再拿真实实例**（`getAll()[0]`）→ 沿 prototype 链（`Object.getPrototypeOf` 循环）列全方法 → `fn.toString()` 看它内部调用的 RPC 名（形如 `extensionApi.<Namespace>.<method>`）。
3. **最后才运行验证**。

三条都不可省：只看命名空间的 key 会漏掉整类能力（`rebuildCopperRegion` 就这么漏过一次）。

## 五、现实适用性隐患（第三维度，容易整个跳过）

- **回退路径**：布不通 / 核查不过 / 自动布线不可用，分别回哪一步？文档没写就是缺陷
- **门禁可判定性**："出口条件"如果依赖主观（"用户看图认可"），必须定义**交付物规格**（视角/比例/标注），否则门禁形同虚设
- **检查频率**：出口条件依赖的检查，是否在出口之前的位置就安排了执行？只在最后跑一次 = 错误累积
- **回归检测**：改版后凭什么判断没引入回归？缺"基线 + 对比"就是缺闭环
- **输入粒度**：要求的判据和提供的输入是否同一粒度（例：要逐网络电流，只给总量级"电压电流"）
- **不可逆动作**：删除、清布线、改规则集，是否有确认与备份
